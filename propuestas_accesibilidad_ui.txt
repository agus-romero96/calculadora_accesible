# Propuestas de Accesibilidad y Diseño de Interfaz

Este documento se divide en dos partes: primero, un análisis de la interfaz actual con propuestas para mejorar radicalmente su accesibilidad para usuarios de lectores de pantalla; segundo, una recomendación sobre cómo manejar la entrada de datos y el rol del atajo "Enter" a medida que la calculadora se vuelve más compleja.

---

## 1. Mejoras de Accesibilidad Reales y de Alto Impacto

La interfaz actual tiene una buena base (etiquetas, nombres en controles, menús), pero podemos mejorar drásticamente la experiencia para usuarios con discapacidad visual con los siguientes cambios:

### a) Anuncios Dinámicos para Resultados y Errores

**Problema:** Cuando un usuario ejecuta una operación, el resultado aparece en el cuadro de texto, pero el lector de pantalla (NVDA, Jaws) no lo lee automáticamente. El usuario tiene que navegar manualmente hasta el cuadro de resultado para escucharlo, lo cual es lento y frustrante.

**Solución de Alto Impacto:** Forzar al lector de pantalla a anunciar cambios importantes.

- **Anunciar el resultado:** Después de calcular y mostrar el resultado en `show_res`, utiliza `wx.CallAfter` para enviar una notificación de accesibilidad. Esto hará que NVDA anuncie el resultado inmediatamente, sin que el usuario tenga que moverse.

  ```python
  # En tu método show_res(self, texto) en ui.py
  import wx.siplib
  
  def show_res(self, texto):
      self.result_text.SetValue(texto)
      self.result_text.SetFocus()
      self.result_text.SetInsertionPoint(0)
      self.ocultar_controles_avanzados()
      
      # ANUNCIO DE ACCESIBILIDAD
      # Usamos CallAfter para asegurar que la UI se actualice primero
      if not wx.siplib.isdeleted(self.result_text):
          wx.CallAfter(self.result_text.Notify)
  ```
  La función `Notify()` le dice a las tecnologías de asistencia que algo ha cambiado en este control y que deben prestarle atención.

- **Anunciar errores de forma explícita:** Un error no es un resultado normal. Debería ser una interrupción clara. En lugar de mostrar el error silenciosamente en el cuadro de resultados, usa un cuadro de diálogo modal.

  ```python
  # Ejemplo de cómo manejar un error
  def on_evaluate(self, e):
      try:
          expresion = self.get_val()
          if not expresion:
              # Esto será leído inmediatamente por el lector de pantalla
              wx.MessageBox("Por favor, escriba una expresión antes de evaluar.", "Error", wx.OK | wx.ICON_ERROR)
              return
          resultado = self.operaciones.EvaluarExpresion(expresion)
          self.show_res(resultado)
      except Exception as err:
          wx.MessageBox(f"Ocurrió un error al procesar la operación:\n\n{str(err)}", "Error de Cálculo", wx.OK | wx.ICON_ERROR)
  ```

### b) Contraste de Color y Tema de Alto Contraste

**Problema:** El `wx.LIGHT_GREY` puede no tener suficiente contraste para personas con baja visión.

**Solución:**
1.  **Verifica el Contraste:** Usa una herramienta online para verificar que el contraste entre el color de fondo y el texto cumple con las pautas WCAG AA (mínimo 4.5:1).
2.  **Ofrece un Tema de Alto Contraste:** Añade una opción en el menú (ej: "Ver" -> "Activar Tema de Alto Contraste") que cambie los colores de la aplicación a un esquema clásico como fondo negro con texto blanco/amarillo. Esto es un estándar de facto en accesibilidad.

### c) Retroalimentación No Visual (Sonidos)

**Problema:** Un usuario vidente puede ver instantáneamente si la operación tuvo éxito o falló. Un usuario de lector de pantalla no.

**Solución:** Añade sonidos opcionales (que se puedan activar/desactivar en un menú de preferencias).
- **Sonido de Éxito:** Un "ding" sutil cuando una operación se completa correctamente.
- **Sonido de Error:** Un "buzz" o un sonido de alerta cuando una operación falla (además del `MessageBox`).

Esto proporciona un canal de retroalimentación inmediato que no depende de la vista.

## 2. Recomendación sobre el Cuadro de Edición y el Atajo "Enter"

Planteas una preocupación muy válida: a medida que la calculadora abarca más áreas (matrices, sistemas de ecuaciones, etc.), un único cuadro de texto se vuelve insuficiente y el atajo "Enter" para "Evaluar" pierde sentido si la intención es otra.

### Mi recomendación es: **NO elimines el cuadro de edición principal NI el atajo "Enter".**

En su lugar, redefine el modelo mental de la aplicación de esta manera:

**El cuadro de texto principal es para el "QUÉ" y el menú es para el "CÓMO".**

1.  **El Cuadro de Texto es para el Objeto Matemático:** El usuario escribe la expresión, la ecuación, la matriz (en formato de texto como `[[1,2];[3,4]]`), etc. Es el sujeto de la operación. Para el 80% de los casos de uso rápido (`2+2`, `sin(pi/2)`), es la forma más rápida de trabajar.

2.  **El Menú (o botones) es para la Acción:** El usuario elige qué hacer con el objeto que escribió.
    - ¿Quiere su valor numérico? -> **Evaluar**
    - ¿Quiere su forma simplificada? -> **Simplificar**
    - ¿Quiere su derivada? -> **Derivar**

3.  **El Atajo "Enter" es para la Acción Más Común:** La acción más frecuente en una calculadora es, por lejos, "Evaluar". Eliminar este atajo obligaría al usuario a realizar acciones adicionales (como `Ctrl+E` o navegar al menú/botón) para la tarea más simple, lo cual es un gran paso atrás en usabilidad y accesibilidad para usuarios de teclado. **Mantén "Enter" como el atajo para "Evaluar"**.

### ¿Cómo escalar a operaciones complejas?

La respuesta es la que ya estás usando: **Diálogos Dedicados para Operaciones Complejas.**

- **Sistemas de Ecuaciones:** No se escriben en el cuadro principal. El usuario va a "Álgebra" -> "Resolver Sistema de Ecuaciones...", y se abre un diálogo que le pide las ecuaciones una por una. **Esto es perfecto.** Es un flujo de trabajo guiado y accesible.
- **Operaciones con Matrices:** Puedes seguir el mismo patrón. El usuario va a "Álgebra" -> "Matrices" -> "Multiplicar Matrices...". Se abre un diálogo que pide "Matriz A" y "Matriz B" en dos cuadros de texto separados.
- **Límites:** Ya lo haces bien. Pides la función, la variable y el punto de tendencia en diálogos separados.

### Conclusión de la Recomendación:

Tu calculadora no debe tener un único método de entrada, sino un **sistema híbrido**:

- **Entrada Rápida:** El cuadro de texto principal para expresiones simples y directas, con `Enter` para la evaluación inmediata.
- **Entrada Guiada:** Diálogos específicos lanzados desde el menú para operaciones complejas que requieren múltiples datos (sistemas, operaciones matriciales, etc.).

Este enfoque te da lo mejor de ambos mundos: la velocidad y eficiencia de una calculadora de línea de comandos para tareas simples, y la claridad y estructura de una GUI para tareas complejas. Eliminar la entrada rápida sería un error que perjudicaría la experiencia de todos los usuarios, especialmente los que dependen del teclado.
